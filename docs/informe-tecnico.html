1. Resumen ejecutivo

En una organización certificada bajo ISO 9001, consultar un procedimiento exige saber tres cosas antes de leer nada: en qué documento está la respuesta, cuál es su versión vigente y en qué cláusula. Hoy eso se resuelve preguntándole a una persona del área de Calidad; cuando esa persona no está, se resuelve adivinando. Actuar sobre una versión derogada no es un despiste: es una no conformidad en auditoría.

NormIA es un asistente conversacional que responde preguntas sobre la documentación vigente citando siempre código, versión y sección, y que no inventa: cuando no tiene respaldo documental, lo dice y ofrece derivar la consulta al Responsable de Calidad. Además registra no conformidades y sus acciones correctivas (ciclo CAPA), detecta inconsistencias al ingerir documentos y produce material de concienciación con la cláusula que lo respalda.

La tesis del proyecto no es «un chatbot que responde» sino trazabilidad auditable. Por eso el diseño combina un modelo de lenguaje con una capa de controles deterministas que pueden descartar una respuesta ya redactada. Medido sobre un banco de 12 consultas reales, el modelo por sí solo acierta 1; con recuperación aumentada acierta 12 de 12 y no cita ningún documento inexistente.

Todo corre en una sola máquina, sin servicios externos: el modelo de lenguaje, los embeddings y la generación de imágenes son locales. No es una optimización sino la condición de partida, porque un sistema de gestión contiene procedimientos internos y organigramas que no pueden viajar a una API de terceros.

2. El problema de negocio

ABISERVI es una empresa peruana de logística con un sistema de gestión de la calidad (SGC) certificado. Su documentación controlada comprende 132 documentos vigentes en 12 áreas (manuales, políticas, procedimientos, instructivos, formatos, planes, organigramas y listas maestras) que suman 1 043 cláusulas numeradas. La unidad de respuesta casi nunca es «el documento»: es una cláusula concreta dentro de él.

Tres síntomas observados

  • El conocimiento está en una persona. Las dudas operativas («¿cuánto tiempo tengo para atender un requerimiento?», «¿qué anillo del arnés vale para detener caídas?») se resuelven preguntando a Calidad. Cuando no está disponible, el operario actúa de memoria.
  • La versión importa tanto como el contenido. Al ingerir el SGC real y cruzarlo contra su Lista Maestra aparecieron discrepancias: CAL-IN-01 figura como v1 en la lista pero imprime v2 en su membrete; varios formatos referenciados por procedimientos vigentes no están registrados.
  • Las no conformidades se pierden entre el aviso y el registro. Un hallazgo reportado de palabra no genera acción correctiva, y el ciclo CAPA que exige la cláusula 10.2 queda a medias.

Por qué inteligencia artificial, y por qué con límites

Un buscador clásico devuelve documentos; lo que la persona necesita es una respuesta en lenguaje natural con su referencia exacta. Un modelo de lenguaje resuelve la redacción, pero introduce el riesgo opuesto: responder con seguridad algo que no está en ningún documento. El problema de negocio, por tanto, no es «responder» sino responder solo cuando hay respaldo y demostrar cuál es. Eso define la arquitectura: el modelo redacta, pero no decide si la respuesta sale.

3. Objetivos y criterios de verificación

ObjetivoCómo se verifica
Responder sobre documentación vigente, citando siempre la fuente Banco de 12 consultas reales (scripts/benchmark_models.py) con la respuesta correcta verificada leyendo el documento. Un documento marcado obsoleto deja de citarse en el mismo instante.
No inventar nunca un documento ni una acción Cada código citado se comprueba contra la base; cada versión citada se corrige contra la real; cada ID de hallazgo o acción correctiva afirmado debe existir. Si no, la respuesta se descarta.

Que ningún documento salga de la organización Modelos locales (LLM, embeddings, difusión). Restricción de partida, no optimización.

Los criterios son medibles y automatizados: 436 tests cubren guardrails, herramientas, enrutado, ingesta, consentimiento, autenticación y seguridad. Un objetivo que no se puede verificar no está en la lista.

4. Metodología de trabajo

El proyecto se desarrolló entre el 27 de agosto y el 22 de octubre de 2026 en 70 commits, con el SGC real del cliente desde el primer día (recomendación explícita de la guía: elegir un problema cuyos datos estén disponibles desde el inicio). Se siguieron cuatro principios:

  1. Medir antes de cambiar. Cada decisión de modelo, umbral o prompt tiene una medición previa y otra posterior. La línea base del modelo de producción se congeló el 24/09/2026 (docs/linea-base.md) antes de entrenar ningún adaptador: un fine-tuning sin línea base no se puede defender.
  2. Los guardrails nacen de fallos observados, no de hipótesis. Cada control tiene documentado el incidente que lo motivó, en el propio código, con el dato medido.
  3. Verificar el hecho, no la redacción. No se buscan frases en la salida del modelo («he registrado…»): se comprueba contra la base si el registro existe. Cazar formulaciones se pierde siempre; un ID o está en la tabla o no está.
  4. Ensayo en vivo como prueba de aceptación. El flujo completo (entrada, consulta, intento de engaño, subida de un PDF, ciclo CAPA, derogación de un documento, cambio de rol) se ejecutó en el navegador antes de dar por cerrada cada fase. Varios defectos descritos en la sección 14 se encontraron así y no en los tests.

5. Arquitectura de la solución

Cuatro capas en una sola máquina. El cliente es un Web Component con Shadow DOM que se incrusta en cualquier intranet sin heredar ni imponer estilos; la API es FastAPI; el núcleo contiene el orquestador, la recuperación, las herramientas, los guardrails y el pipeline de ingesta; los modelos (Qwen3.8 27B vía Ollama y BAAI/bge-m3) corren en local; y PostgreSQL 16 con pgvector guarda documentos, cláusulas, conversaciones, hallazgos, acciones correctivas, escalaciones, usuarios y la traza de auditoría en un solo motor. El prototipo corre en una sola máquina; el mismo código se despliega en un servidor para n usuarios cambiando configuración, no código (sección 15).

6. Recuperación aumentada sobre documentos controlados

Troceado por cláusula, no por tamaño. En un documento controlado la unidad de sentido es la cláusula («6.1.2», «7.4 Recepción y conformidad»). Trocear así es lo que permite citar «sección 7.2.4» con trazabilidad. Las tablas se extraen como texto estructurado (los tiempos de atención de TI viven en una tabla).

Dos búsquedas en paralelo. La pregunta se vectoriza una vez y se compara con el banco de 730 preguntas frecuentes verificadas (generadas desde las cláusulas y comprobadas una a una contra su texto) y con las cláusulas de documentos vigentes. Un documento marcado obsoleto desaparece del índice de búsqueda sin reindexar nada: es un filtro en la consulta.

Umbral absoluto y margen relativo. ORDER BY distancia LIMIT k siempre devuelve algo, por irrelevante que sea. El umbral (RAG_MAX_DISTANCE = 0,527, calibrado con scripts/calibrate_threshold.py) más un margen relativo del 8 % sobre el mejor resultado convierten la búsqueda en un guardrail: sin contexto suficiente, el modelo no redacta.

Carga directa de sección. Si el usuario pide «la sección 6.2 del COM-PR-01», no se pasa por el vector: se carga la cláusula exacta.

Traza de auditoría. Cada turno guarda qué se recuperó, a qué distancia, qué herramienta se llamó y si la respuesta quedó fundamentada (messages.retrieval_debug). Es lo que permite reconstruir, meses después, por qué el asistente dijo lo que dijo.

7. Guardrails: controles deterministas

Cinco controles pueden descartar una respuesta ya redactada. Todos son código, no instrucciones al modelo, y cada uno existe porque se observó el fallo que evita:

ControlEl fallo que lo motivóQué hace
1. Umbral semánticoSin un mínimo de parecido, la búsqueda siempre devuelve algo.Sin contexto, no se redacta: se ofrece derivar.
2. Versión citadaEscribió «STI-PO-01 v1» cuando el documento está en v2, contradiciendo su propia ficha de fuentes.Corrige la versión contra la real y lo anota en la traza.
3. Código citadoCitó PROC-CAL-04, que no existe: lo copió del ejemplo de formato de su propio prompt.Un código inexistente invalida la respuesta entera.
4. FundamentaciónPrometía derivar a Calidad sin que se registrara nada; se contaron 39 escalaciones sin registro.La derivación existe en base o no se anuncia.
5. Registro afirmadoRespondió «la acción correctiva quedó registrada con el ID 100» sin haber ejecutado ninguna herramienta; la última acción era la 9.Todo ID de hallazgo o acción afirmado se busca en la base. Si no está, se sustituye la respuesta.

Por qué deterministas. El modelo local a veces escribe la llamada a herramienta como texto en vez de emitirla; el turno «funciona», no hay error, y la herramienta nunca se ejecuta. Un control que dependa de que el modelo se acuerde de algo desaparece en silencio justo cuando hace falta. Por eso el consentimiento para derivar, la verificación de citas y la de registros no son herramientas: son código que se ejecuta siempre.

Consentimiento antes de derivar. Nada entra en la bandeja de Calidad sin que el usuario diga que sí. Toda respuesta que deje una propuesta de derivación abierta termina con la misma pregunta, venga de un guardrail o de una herramienta, y el turno siguiente se resuelve comprobando eso. Antes de este control la bandeja acumuló 306 consultas que nadie había pedido derivar; una bandeja así se deja de mirar.

Otros controles previenen antes de llegar ahí: filtro de alcance con suelo determinista y juicio del modelo para el material visual, detección de inyección de prompt en la escena, recuperación de llamadas a herramienta escritas como texto, cortacircuitos ante fallos del LLM, límite de peticiones por IP y tiempo máximo por consulta.

8. El agente y sus herramientas

No es un enrutador de intenciones: las nueve herramientas se exponen por function calling y el modelo elige. Cuatro de ellas tienen efecto real sobre la base de datos.

HerramientaQué haceEfecto
buscar_documentos«¿Tienen políticas de TI?»: consulta el catálogo por título, código y área.lectura
leer_documentoResume un documento completo y ofrece navegar sus secciones.lectura
register_findingRegistra una no conformidad con severidad y área.escribe
ampliar_hallazgoAñade detalle a un hallazgo ya registrado.escribe
registrar_accion_correctivaCierra el ciclo CAPA: exige acción, responsable y fecha; deduplica.escribe
get_capa_statusEstado de las acciones correctivas de un hallazgo.lectura
escalate_to_qualityPropone la derivación al responsable humano y la deja registrada, pendiente de confirmación.escribe
describir_capacidadesResponde sobre sí mismo sin consultar el SGC.—
generar_material_visualPrepara un cartel con respaldo documental y lo entrega a la página de material visual.—

El ciclo CAPA, en un hilo. El operario cuenta lo que vio; el agente lo clasifica (menor, mayor, observación), lo registra y pregunta quién se encargará y para cuándo. Con esos dos datos registra la acción correctiva y el hallazgo pasa a «en revisión». La fecha relativa («antes del 15 de noviembre») se interpreta con la fecha del día inyectada en el prompt: sin ella el modelo devolvía fechas del año anterior y la acción nacía vencida.

9. Fine-tuning con QLoRA

El objetivo del fine-tuning no era que el modelo «supiera» el SGC (eso lo resuelve la recuperación) sino que respondiera en el formato del producto: cita con código, versión y sección; llamada a herramienta como tool call y no como texto; negativa con escalación cuando no hay respaldo.

Dataset

584 ejemplos ensamblados de lo que el proyecto ya tenía verificado, no redactados a mano (scripts/build_finetune_dataset.py):

FamiliaEjemplosQué enseña
cita400Responder con respaldo y citar código, versión y sección (de las 730 FAQ verificadas; recortada para no ahogar a las demás).
herramienta135Emitir la llamada como tool call, no escribirla en el texto.
escalacion31Negarse y llamar a escalate_to_quality sin respaldo.
fantasma14No citar un documento inexistente (los 14 rechazos documentados del FAQ).
social4Saludar sin escalar a Calidad.

Reparto 468 / 57 / 59 (train / valid / test) por grupo de cláusula de origen, no por ejemplo: dos preguntas de la misma cláusula comparten casi todo el prompt y separarlas convertiría la validación en una medida de memorización. Las 12 preguntas del banco de pruebas quedan fuera de las tres particiones.

Entrenamiento

QLoRA sobre mlx-community/Qwen3-4B-4bit con MLX en Apple Silicon: 0,365 % de parámetros entrenables (14,7 M de 4 022 M), 400 iteraciones, tasa de aprendizaje 1e-4, memoria pico 11,3 GB. Pérdida de validación de 2,259 a 0,221; pérdida en test 0,284 (perplejidad 1,33). Registro completo en docs/entrenamiento.log.

Resultado

Sobre las 12 consultas excluidas del entrenamiento, el modelo base acierta 11 de 12 y el afinado 12 de 12 (docs/comparacion-lora.md, con las respuestas completas de ambos). Lo que cambia no es tanto el acierto como la forma: la respuesta pasa de una mediana de 1 014 a 160 caracteres y cita de forma más consistente. Es un resultado independiente y medido, como pide la guía, y se presenta separado del que aporta el RAG.

Un efecto secundario medido: el fine-tuning empeoró la emisión de llamadas a herramienta del 100 % al 75 % en una de las mediciones. Entrenar una llamada como texto la empuja hacia su forma de texto. El control de «registro afirmado» de la sección 7 existe en parte por esto.

10. Generación de material visual

ISO 9001 pide formar y comunicar (cláusulas 7.2, 7.3 y 7.4). El material de concienciación no es decoración: da servicio a tres cláusulas del estándar. NormIA genera carteles y señalética que citan la cláusula que los respalda, y la cita se valida contra el catálogo: no se puede imprimir un respaldo que no existe.

  • La escena la escribe el usuario en castellano; el modelo la traduce a un prompt telegráfico en inglés y juzga si está dentro del alcance de un sistema de gestión (un suelo determinista rechaza lo inaceptable; el resto lo decide el modelo, incluida la detección de inyección de prompt en la propia escena).
  • SDXL base + refinador en MPS, con el VAE de precisión corregida. El refinador trabaja sobre la imagen decodificada, no sobre latentes: el traspaso en latentes desbordaba en fp16 y devolvía imágenes negras.
  • El texto no lo dibuja el modelo. El titular, el logotipo real y la cita de la cláusula se componen encima; el modelo solo dibuja la escena. Un modelo de difusión escribe letras ilegibles.
  • Los prompts caben en 77 tokens. CLIP corta en 77 sin avisar; el negativo llegó a tener 135 y el modelo descartaba 58, entre ellos los términos contra deformidades. Un test lo mide con el tokenizador real.
  • Licencia. SDXL es CreativeML OpenRAIL++-M: permite el uso como servicio pero obliga a propagar sus restricciones; condiciones.html las muestra al usuario. En producción se sustituiría por FLUX.1 (Apache 2.0).

14. Limitaciones

Se enumeran las que un tribunal preguntaría primero, incluidas las encontradas en el ensayo final. Ninguna está maquillada.

  1. El banco son 12 consultas. Suficiente para ver un patrón, corto para afirmar un porcentaje con intervalo de confianza.
  2. Contenido inventado con cita real. Preguntado por cotizaciones de compras, el sistema respondió «tres cotizaciones para compras mayores a 1 000 soles» citando COM-PR-01 v3, sección 6.1.2. El documento existe, la sección existe, pero dice «una cotización» y no hay umbral alguno: la búsqueda trajo una plantilla en blanco titulada «Cotización» y el modelo rellenó el hueco con conocimiento general. El sistema lo detecta (evento citation_not_retrieved: el código citado no estaba entre lo recuperado) pero hoy solo lo registra. Conectarlo como bloqueo es el siguiente cambio, y el más importante.
  3. La llamada a herramienta no es fiable turno a turno. El modelo local a veces escribe en prosa que registró algo sin emitir la llamada. El control de registro afirmado lo convierte en un mensaje veraz y recuperable, pero no lo evita. Ollama ignora tool_choice, así que no se puede forzar.
  4. El fine-tuning empeoró la emisión de llamadas del 100 % al 75 % en una medición.
  5. 24 cláusulas del SGC son imágenes y una está escaneada: hoy se descartan en la ingesta. Harían falta OCR y un modelo de visión.
  6. Deduplicación de hallazgos por huella: dejó pasar dos registros casi idénticos del mismo extintor con redacción distinta.
  7. Al borrar un documento, su trabajo de subida queda huérfano en la lista de revisión.
  8. El material visual no entra en documentos controlados. Formación sí; documento del SGC no: sería un problema de auditoría.
  9. Sin pruebas de carga. Generar una imagen bloquea un hilo 44 s; el límite de peticiones y el cortacircuitos viven en memoria del proceso.

15. Conclusiones y próximos pasos

Lo que el proyecto demuestra. Un modelo de lenguaje local, sin los documentos delante, acierta 1 de 12 consultas sobre un SGC real e inventa códigos de procedimiento. Con recuperación por cláusula, umbral semántico y una capa de controles deterministas, acierta 12 de 12 y no cita nada que no exista. El fine-tuning, medido por separado sobre casos no vistos, mejora el formato sin penalizar la latencia. El agente cierra el ciclo de no conformidad con registros reales, verificables en la base, y nada se deriva a Calidad sin consentimiento.

Lo que aprendimos. Los fallos más caros no fueron de precisión sino de promesa incumplida: el sistema afirmando que había derivado, registrado o generado algo que no existía. Todos se resolvieron del mismo modo, verificando el hecho contra la base en vez de confiar en la redacción. Y los defectos más importantes se encontraron ensayando el flujo completo en el navegador, no en los tests: la cobertura automatizada no sustituye el uso real.

Despliegue en servidor para n usuarios

El objetivo de producto es un servidor al que consulten decenas o cientos de personas, no un portátil. Lo que hace eso viable ya está resuelto: PostgreSQL con pgvector escala sin tocarlo, la sesión es una cookie firmada sin estado en el servidor, el cliente del LLM habla el protocolo de OpenAI (vLLM entra con tres variables) y los guardrails son código determinista que corre igual en cada worker.

Lo que hoy vive en memoria del proceso y hay que sacar fuera para tener varios workers:

PiezaHoyPara n usuarios
Límite de peticionesVentana deslizante en RAM del procesoRedis: con cuatro workers, cada uno llevaría su propia cuenta.
Cortacircuitos del LLMEn el cliente, por procesoRedis, por la misma razón.
Ingesta de PDFBackgroundTasks dentro de la APICola de trabajos: un PDF grande no debe ocupar un worker web.
Generación de imagenSíncrona, 44 s bloqueando un hiloWorker aparte o serverless; la API devuelve un ticket.

Nada de esto es un rediseño: es mover estado fuera del proceso. El orquestador, las herramientas y los controles no cambian.

Capacidad y coste

Qwen3 27B cuantizado a 4 bits ocupa unos 16 GB de GPU; la concurrencia típica de 100 usuarios reales es de 5 a 10 consultas simultáneas, así que una GPU basta.

El coste de la generación de imagen es despreciable frente al del LLM: el material visual es de volumen mínimo y puede pagarse por segundo de GPU.

16. Instrucciones de instalación y uso

Requisitos: macOS o Linux, Docker, Python 3.12 (uv lo instala), Ollama con el modelo indicado y unos 24 GB de memoria para el LLM. La generación de imágenes necesita 13 GB adicionales durante la pieza.

git clone https://github.com/klauzirrazabal-max/normia-chatbot-iso.git
cd normia-chatbot-iso
cp .env.example .env                       # revisa LLM_MODEL, DATABASE_URL, ADMIN_API_KEY
docker compose -f docker/docker-compose.yml up -d     # PostgreSQL 16 + pgvector
uv sync                                    # Python 3.12 y dependencias con lockfile
ollama pull qwen3.8:27b-mlx

uv run python scripts/seed_demo_tenant.py --tenant demo-publica --name "Empresa Demo"
uv run python scripts/ingest_docs.py --tenant demo-publica     # troceado por cláusula + embeddings
uv run python scripts/load_registry.py --tenant demo-publica   # Lista Maestra
uv run python scripts/crear_usuario.py calidad@empresa.com --rol calidad

uv run uvicorn app.main:app --port 8000
# http://localhost:8000  →  acceso, inicio, asistente, material visual, gestión documental

uv run pytest -q                           # 436 tests

El README.md (913 líneas) documenta cada decisión, el umbral de distancia, la comparación de modelos y la verificación.
